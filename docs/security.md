# Security

## Signing in

- **Shop staff:** username and a 4 to 6 digit PIN, hashed with scrypt (Better Auth). Five wrong PINs lock the account for 5 minutes. An unknown username, a wrong PIN and another shop's staff on this address all get the same answer, and only the shop's own staff count towards a lockout, so nobody can lock out another shop's staff.
- **Console:** email and a password of at least 10 characters. Five wrong passwords lock the account for 15 minutes. The console sign in refuses shop accounts before checking anything, so it cannot be used to guess PINs.
- **Sessions:** an `HttpOnly`, `Secure`, `SameSite=Strict` cookie, valid for 12 hours. Each address gets its own cookie, so a till session never reaches the console and the reverse. Switching a person off, changing their role or branches, or resetting their PIN or password ends their sessions at once.
- Public sign up does not exist. Shop accounts are made by an owner or by the console. Console accounts are made by a super admin or the command line.

## Who can see what

- Every API request is checked on the server for role, branch and business. Hiding a button is never the control.
- One client can never see or change another's data: queries are scoped to the signed in business, a record from another business answers 404, and a session only works on its own business's address. Tests prove this for every area.
- The console API is only reachable on the console's address, and the shop API only on shop addresses (nginx enforces it as well as the API).

## Money and records

- The database refuses impossible money states (CHECK constraints): negative amounts, totals that do not add up, overpaid invoices, an M-Pesa code used twice.
- Paid sales cannot be edited. Only a refund approved by a manager reverses one, and every refund, discount and cancellation needs someone other than the requester to approve it (owners excepted).
- The activity log is append only: a database trigger refuses any update or delete.

## Secrets

- `db.env` and `api.env` are generated on the server on the first deploy, readable only by the `liban` user, and never committed or copied anywhere.
- Each shop's Daraja keys are encrypted with AES-256-GCM before they are stored (`src/lib/secrets.ts`). The API never returns them, only their last four characters. They are never written to the activity log.
- The M-Pesa callback address contains a secret token compared in constant time. A callback only counts if it matches a request we sent, including the amount.
- PINs and temporary passwords generated by the console are shown once and never stored in plain or logged.

## Web protections

- HTTPS only, with HSTS. Content Security Policy limits scripts, styles, fonts and connections to the site itself (and Google Fonts). Pages cannot be framed.
- State changing requests from an origin that is not trusted are refused, on top of the SameSite cookie.
- The shop is read from the `Host` header only; `X-Forwarded-Host` is ignored so it cannot be forged.
- Request bodies are limited to 100 KB, and every input is validated (Zod) before use. SQL is always parameterised.
- CSV exports neutralise spreadsheet formulas in every cell.

## What is recorded

The activity log keeps who did what and when: sign ins and failed attempts, sales, payments, refunds, approvals, stock changes, staff and settings changes, exports, and everything the Flarehub team does to a client. It never contains PINs, passwords, keys or session tokens. A shop owner sees their own business's entries, with Flarehub team actions shown as "Bottle Point support".

## Operating safely

- Copy backups off the server regularly ([Operations](operations.md#backups)).
- Keep the super admin list short, and use Support or Billing roles for everyone else.
- Before a client goes live with real money, turn on real M-Pesa in their Settings and test it with a small payment.
